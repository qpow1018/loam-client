# LoaM 큰 작업 오케스트레이션

큰 작업을 조사, 설계, 구현, 검증 단계로 나누고 필요한 전문가만 투입한다. 메인 에이전트가 작업 지휘자로서 사용자 소통, 역할 선택, 의견 통합, 최종 결정을 끝까지 소유한다.

## 기본 원칙

- 모든 역할을 한꺼번에 생성하지 말고 현재 단계에 필요한 역할만 선택한다.
- 현황 조사관과 독립 검증자는 큰 작업의 기본 역할로 둔다.
- 분석·설계 단계의 전문가는 읽기 전용으로 작업한다.
- 저장소의 `AGENTS.md`와 관련 기능 문서에서 확인한 지원 환경, 제품 범위, 검증 명령을 실행 계약의 최상위 제약으로 취급한다.
- 지원하지 않는 플랫폼이나 환경을 일반적인 모범 사례라는 이유로 설계·구현·검증 범위에 추가하지 않는다.
- 구현을 병렬화할 때는 수정 가능한 파일 범위를 겹치지 않게 배정한다.
- 여러 역할이 같은 파일을 수정해야 하면 작업 지휘자가 해당 파일을 소유하거나 순차 작업으로 전환한다.
- 전문가의 제안을 그대로 전달하지 말고 실제 저장소 근거와 사용자 목표를 기준으로 하나의 결정으로 통합한다.
- 서브에이전트 수가 제한되면 단계를 나눠 실행하고, 역할 수를 채우기 위해 불필요한 에이전트를 생성하지 않는다.
- 조건에 해당하는 역할은 가용 슬롯이 없다는 이유로 생략하지 말고 다음 단계로 예약한다.
- 새 의존성, 테스트 러너, CI, 빌드·배포 기반, 공용 컴포넌트·레이아웃 변경은 별도 승인 항목으로 제안하고 명시적 승인 전에는 수정하지 않는다.
- 사용자 요청이 부여한 수정, 커밋, 배포, 운영 변경 권한을 넓히지 않는다.
- 시스템 설계자가 구현 전 실행 계약을 설계하고 작업 지휘자가 통합·확정하며, 독립 검증자가 구현 후 충족 여부를 판정한다.
- 큰 작업은 조사·설계 결과를 반영한 실행 계약을 사용자에게 제시하고 명시적 승인을 받은 뒤에만 구현한다. 최초 요청에 구현 의사가 포함됐더라도 아직 제시되지 않은 실행 계약의 승인으로 간주하지 않는다.
- 다른 역할은 실행 계약을 임의로 바꾸지 않는다. 새로운 제품, 구조, 데이터 의미, Auth/RLS, migration, 보안, rollback 또는 production-state 결정은 작업 지휘자와 시스템 설계자에게 되돌린다.
- 이 스킬은 사용자가 적용을 명시적으로 승인한 뒤에만 시작한다. 승인 전에는 적용 여부만 사용자에게 확인하고, 조사·역할 투입·실행 계약 절차를 시작하지 않는다.

## 커스텀 에이전트 설정

- `.codex/agents/<name>.toml`을 해당 역할의 이름, 모델, 추론 강도, sandbox, 실행 지침의 단일 원본으로 취급한다.
- 커스텀 에이전트 선택을 지원하면 아래 역할 이름으로 생성한다.
- 현재 실행 환경이 커스텀 에이전트 이름을 직접 선택하지 못하면 해당 TOML을 읽고 `model`과 `model_reasoning_effort`를 spawn override로 전달한다. `sandbox_mode`를 지키고 `developer_instructions`를 인계 프롬프트에 포함한다.
- 명시적 모델 override를 사용할 때는 필요한 맥락만 전달하고, 모델 변경을 막는 전체 대화 상속 방식은 피한다.
- 사용자 지정 모델과 추론 강도를 우선한다. TOML과 충돌하면 커스텀 에이전트 이름 대신 같은 역할 지침과 사용자 설정으로 생성한다. 적용할 수 없는 설정은 안전하게 상속하고 항목을 결과에 남긴다.
- 작업 지휘자인 메인 에이전트의 모델은 고정하지 않는다.

## 역할 선택

메인 에이전트가 작업 지휘자를 맡아 목표와 완료 기준, 역할과 순서, 실행 계약, 통합 diff, 최종 보고를 소유한다. 별도 작업 지휘자는 생성하지 않는다.

- `loam_investigator` (현황 조사관): 큰 작업의 초기 조사에 기본 투입한다. 현재 동작, 영향 경로, 재사용·검증 수단, 위험과 미확인 사항을 받는다.
- `loam_product_experience` (제품·경험 설계자): 사용자 흐름이나 정보 구조가 크게 바뀔 때 투입한다. 핵심 흐름과 상태, 정보 계층, 접근성, 제품 완료 기준을 받는다.
- `loam_ui_designer` (UI·비주얼 디자이너): 새 화면, 큰 UI 변경, 기존 화면과의 시각적 일관성 검토에 투입한다. 구현 전에는 실제 기준 화면에서 레이아웃·크기·위치·간격·타이포그래피·밀도 계약을 만들고, 구현 후에는 같은 viewport에서 계약 충족을 다시 판정한다.
- `loam_system_architect` (시스템 설계자): 여러 모듈, 데이터·인증 경계, migration 또는 큰 구조 변경에 투입한다. 목표 구조, 계약, 파일 소유권, 순서와 위험을 받는다.
- `loam_frontend_worker` (프론트엔드 구현자): React, Next.js, TanStack Query, 클라이언트 저장소, UI 또는 SCSS 변경에 투입한다.
- `loam_backend_worker` (백엔드·데이터 구현자): API, 서버·인증, Supabase, migration, Edge Function, 외부 연동 또는 DB 계약 변경에 투입한다.
- `loam_independent_verifier` (독립 검증자): 통합 구현 후 기본 투입한다. 요구사항·계약·diff·검증 로그를 비교한 판정과 근거를 받는다.
- `loam_release_guardian` (릴리스 보호자): production-sensitive 데이터, Auth/RLS, Edge Function, 환경 변수, 배포 또는 PWA 변경에만 투입한다. 적용 전 검사, 실행·복구 순서와 적용 후 검증을 받는다.

## 실행 절차

### 1. 작업을 판별한다

- 저장소 루트부터 작업 경로까지 적용되는 `AGENTS.md`와 관련 기능 문서를 먼저 읽는다.
- 목표, 비범위, 제약, 완료 기준을 먼저 적는다.
- 지원 플랫폼, 대상 브라우저, viewport 범위, PWA와 모바일 지원의 관계를 저장소 근거 또는 사용자 답변으로 확정한다.
- 기존 테스트·빌드 기반, dirty worktree, 새 의존성·설정 필요 여부, 사용자 확인 시점과 커밋 경계를 확인한다.
- 중요한 해석 차이가 결과를 바꾸면 구현 전에 사용자에게 확인한다.
- 안전한 가정으로 진행할 수 있으면 가정과 이유를 밝히고 계속한다.
- 작은 작업이면 이 스킬의 다중 역할 절차를 적용하지 않는다.
- 큰 작업이라도 사용자가 이 스킬 적용을 명시적으로 승인하기 전에는 절차를 시작하지 않는다. 승인 후 역할별 선택 여부, 투입 단계, 선택하거나 생략한 이유를 역할 선택표로 남긴다.
- 실행 계약이 승인되기 전에는 읽기 전용 조사·설계만 수행한다.

### 2. 조사 단계를 실행한다

- 현황 조사관에게 적용되는 `AGENTS.md`, 관련 문서, 지원 환경, 기존 검증 기반과 dirty worktree를 확인하도록 읽기 전용 범위와 조사 질문을 전달한다.
- 새 화면이나 큰 UI 변경이면 제품·경험 설계자와 UI·비주얼 디자이너를 함께 투입한다. UI·비주얼 디자이너는 선언된 viewport에서 현재 화면과 유사한 기존 화면 2~3개를 실제 브라우저로 비교한다.
- UI와 시스템 설계가 모두 필요하면 제품·경험 설계자, UI·비주얼 디자이너, 시스템 설계자를 같은 읽기 전용 단계에서 병렬 실행한다.
- 가용 슬롯이 부족하면 조사, 제품·경험 설계, 시스템 설계를 순차 단계로 실행한다.
- 역할을 합쳐도 독립적인 관점이 사라지지 않는 작은 범위에서만 역할을 겸임시키고 이유를 기록한다.
- 각 결과에서 관찰된 사실, 제안, 미확인 사항을 분리한다.

### 3. 실행 계약을 만든다

전문가 결과를 통합해 다음 내용을 짧게 확정한다.

- 목표와 비범위
- 저장소에서 확인한 근거
- 지원 플랫폼, 대상 브라우저와 viewport, 검증 대상 환경
- 제품과 기술 결정
- 비주얼 계약: 기준 화면, 페이지 canvas와 헤더 아래 시작 위치, grid·패널 크기, 간격, 타이포그래피, 컴포넌트·표 밀도, overflow와 주요 상태
- 별도 승인이 필요한 새 의존성, 테스트 러너, CI, 빌드·배포 기반, 공용 컴포넌트·레이아웃 변경
- 구현 단위와 담당 역할
- 역할별 수정 가능 파일과 수정 금지 범위
- 사용자 확인 시점과 예정 커밋 경계
- 완료 기준과 검증 방법
- 남은 위험과 사용자 결정이 필요한 항목

실행 계약을 사용자에게 제시하고 명시적 승인을 기다린다. 제품 방향, 데이터 의미, 지원 환경, 공유 영향, 기반 변경처럼 결과를 크게 바꾸는 항목은 묶어서 암묵적으로 승인받지 말고 항목을 드러내 확인한다.

### 4. 구현 단계를 실행한다

- 승인된 실행 계약이 없으면 구현자를 투입하거나 파일을 수정하지 않는다.
- 프론트엔드와 백엔드 파일 소유권이 분리되면 구현자를 병렬 실행한다.
- 공유 타입, 설정, 공통 계약처럼 겹치는 파일은 작업 지휘자가 소유하거나 구현 순서를 정한다.
- 각 구현자에게 승인된 실행 계약과 비주얼 계약, 저장소 제약, 지원 환경, 목표, 허용 경로, 금지 경로, 결정사항, 완료 기준, 검증 명령을 명시한다.
- 실행 계약에 없는 모바일·반응형 대응, 의존성, 테스트 러너, 공용 컴포넌트·레이아웃 변경을 임의로 추가하지 못하게 한다.
- 구현자가 범위 밖 문제를 발견하면 임의로 수정하지 말고 작업 지휘자에게 보고하게 한다.

### 5. 통합한다

- 실제 diff와 작업 트리 상태를 확인한다.
- 구현 결과가 실행 계약과 기존 프로젝트 경계를 지키는지 검토한다.
- UI 변경은 UI·비주얼 디자이너가 구현 전과 같은 기준 화면·viewport에서 실제 화면을 다시 확인하게 한다. 승인된 비주얼 계약과 다른 크기·위치·간격·계층·밀도는 구현 수정 대상으로 처리하고, 새로운 디자인 결정은 사용자 승인 단계로 되돌린다.
- 승인되지 않은 기반 변경이나 공유 영향이 발견되면 통합하지 않고 사용자 승인 단계로 되돌린다.
- 중복 구현, 충돌, 임시 코드, 누락된 정리를 해결한다.
- 변경 범위에 맞는 가장 작은 검증부터 실행한다.

### 6. 독립 검증한다

- 독립 검증자에게 사용자의 원래 요청, 실행 계약, 실제 diff, 검증 로그를 제공한다.
- 독립 검증자는 저장소와 실행 계약이 지원하지 않는 플랫폼을 결함으로 보고하지 않는다.
- 승인되지 않은 의존성, 테스트 러너, 공통 설정, 공용 컴포넌트·레이아웃 변경은 차단 문제로 판정한다.
- 승인된 비주얼 계약의 너비, 위치, 간격, 정렬, 타이포그래피, 컴포넌트 밀도 위반은 style-only finding이 아니라 계약 위반으로 판정한다.
- 구현자의 기대 결론이나 자기평가를 정답처럼 전달하지 않는다.
- 차단 문제가 발견되면 원래 구현자 또는 작업 지휘자가 수정하고 관련 검증을 반복한다.
- 수정 후 독립 검증자가 영향을 다시 확인하게 한다.
- 독립 검증 PASS는 기술 계약 충족을 의미하며 사용자 제품 승인이나 작업 완료를 대신하지 않는다.

### 7. 릴리스 경계를 확인한다

- 운영 영향이 있을 때만 릴리스 보호자를 투입한다.
- 릴리스 보호자는 읽기 전용으로 계획과 검증을 담당하고, 실제 상태 변경은 작업 지휘자가 사용자 권한 범위에서 수행한다.
- 로컬 검증, dry run, 실제 적용, 적용 후 확인을 별도 단계로 유지한다.
- 배포가 DB migration을 대신한다고 가정하지 않는다.

### 8. 완료를 보고한다

- 구현 결과와 사용자에게 중요한 결정을 먼저 설명한다.
- 실행한 검증과 결과, 실행하지 못한 검증, 남은 위험을 구분한다.
- 예상하지 않은 작업 트리 변경이 없는지 확인한다.
- 사용자가 요청하지 않은 커밋, push, 배포, production 변경은 수행하지 않는다.
- UI·제품 기능은 독립 검증을 통과해도 사용자 확인 전에는 `기술 검증 완료 · 사용자 검토 대기`로 보고한다.
- 다음 상태 중 현재 상태를 명시한다: `조사 중`, `실행 계약 승인 대기`, `구현 중`, `기술 검증 완료 · 사용자 검토 대기`, `완료`.

## 서브에이전트 인계 형식

각 역할 요청에는 다음 내용을 포함한다.

- 역할과 단일 목표
- 필요한 저장소 및 사용자 맥락
- 승인된 실행 계약과 지원 환경
- UI 역할이면 비주얼 계약, 기준 화면과 검증 viewport
- 읽기 전용 또는 수정 가능 여부
- 허용 경로와 금지 경로
- 반환할 산출물
- 완료 조건과 검증
- 판단이 필요한 경우 멈추고 보고할 기준

각 역할은 결론, 근거, 대상 파일, 위험, 검증 결과 순서로 간결하게 보고하게 한다.
