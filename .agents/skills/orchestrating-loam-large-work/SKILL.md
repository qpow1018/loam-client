# LoaM 큰 작업 오케스트레이션

큰 작업을 조사, 설계, 구현, 검증 단계로 나누고 필요한 전문가만 투입한다. 메인 에이전트가 작업 지휘자로서 사용자 소통, 역할 선택, 의견 통합, 최종 결정을 끝까지 소유한다.

## 기본 원칙

- 모든 역할을 한꺼번에 생성하지 말고 현재 단계에 필요한 역할만 선택한다.
- 현황 조사관과 독립 검증자는 큰 작업의 기본 역할로 둔다.
- 분석·설계 단계의 전문가는 읽기 전용으로 작업한다.
- 구현을 병렬화할 때는 수정 가능한 파일 범위를 겹치지 않게 배정한다.
- 여러 역할이 같은 파일을 수정해야 하면 작업 지휘자가 해당 파일을 소유하거나 순차 작업으로 전환한다.
- 전문가의 제안을 그대로 전달하지 말고 실제 저장소 근거와 사용자 목표를 기준으로 하나의 결정으로 통합한다.
- 서브에이전트 수가 제한되면 단계를 나눠 실행하고, 역할 수를 채우기 위해 불필요한 에이전트를 생성하지 않는다.
- 조건에 해당하는 역할은 가용 슬롯이 없다는 이유로 생략하지 말고 다음 단계로 예약한다.
- 새 의존성, 테스트 러너, CI, 배포 기반은 작업에 필요해 보여도 별도 범위로 제안하고 사용자 승인 없이 포함하지 않는다.
- 사용자 요청이 부여한 수정, 커밋, 배포, 운영 변경 권한을 넓히지 않는다.

## 역할 선택

### 작업 지휘자

메인 에이전트가 항상 담당한다. 별도 서브에이전트로 생성하지 않는다.

- 목표, 비범위, 제약, 완료 기준을 정리한다.
- 역할과 실행 순서를 선택한다.
- 전문가 사이의 충돌을 해결하고 실행 계약을 만든다.
- 통합 diff, 검증 결과, 남은 위험을 직접 확인한다.
- 사용자에게 필요한 결정과 최종 결과를 전달한다.

### 현황 조사관

큰 작업이면 기본으로 생성한다. 구현하거나 파일을 수정하지 않는다.

- 현재 동작과 관련 코드 경로를 확인한다.
- 데이터 흐름, 기존 재사용 요소, 검증 수단을 찾는다.
- 영향 범위, 위험, 확인되지 않은 가정을 구분한다.
- 사실 검증이 필요한 도메인 규칙은 출처와 불일치를 함께 보고한다.
- 후속으로 필요한 역할을 근거와 함께 제안한다.

### 제품·경험 설계자

새 사용자 흐름, 화면, 상호작용, 정보 구조가 생기거나 크게 바뀔 때 생성한다.

- 대상 사용자, 해결할 문제, 핵심 흐름을 정의한다.
- 로딩, 빈 상태, 오류, 성공 상태를 빠짐없이 정리한다.
- 화면 위계, 상호작용, 반응형, 접근성 결정을 제안한다.
- 사용자 관점의 완료 기준과 열려 있는 제품 결정을 구분한다.

### 시스템 설계자

여러 모듈, 데이터 계약, 저장소 경계, 인증, migration 또는 큰 리팩터링이 연결될 때 생성한다.

- 현재 구조와 목표 구조를 비교한다.
- 컴포넌트, API, DB, 외부 시스템 사이의 데이터 흐름을 설계한다.
- 변경할 계약, 파일 소유권, 구현 순서를 제안한다.
- 보안, 호환성, migration, 회귀 위험을 식별한다.
- 요청 범위를 넘는 추상화와 선행 리팩터링을 배제한다.

### 프론트엔드 구현자

React, Next.js route, TanStack Query, 클라이언트 저장소, UI 또는 SCSS 변경이 있을 때 생성한다.

- `$following-loam-frontend-style`을 적용한다.
- 실행 계약과 배정된 파일 범위 안에서만 수정한다.
- 사용자 상태와 서버 상태의 경계를 유지한다.
- 관련 lint, 화면 확인, 빌드 등 배정된 검증을 실행한다.

### 백엔드·데이터 구현자

`src/api`, `src/lib`, Supabase Auth/RLS, migration, Edge Function, 외부 API 또는 DB 계약 변경이 있을 때 생성한다.

- `$following-loam-backend-boundaries`를 적용한다.
- 실행 계약과 배정된 파일 범위 안에서만 수정한다.
- 인증, 소유권, 비밀, 데이터 매핑, 환경 경계를 검증한다.
- 관련 lint, SQL, 정책, 함수, 빌드 검증을 실행한다.

### 독립 검증자

통합 구현이 끝나면 기본으로 생성한다. 첫 검토에서는 파일을 수정하지 않는다.

- 원래 사용자 요청, 실행 계약, 실제 diff, 검증 로그를 독립적으로 비교한다.
- 요구사항 누락, 회귀, 보안, 데이터 손상, 과도한 변경을 찾는다.
- 발견 사항을 우선순위, 근거, 영향, 재현 또는 확인 방법과 함께 보고한다.
- 차단 문제가 없을 때만 통과로 판정한다.

### 릴리스 보호자

production 데이터, Supabase migration, Auth/RLS, Edge Function, 환경 변수, 배포 설정 또는 PWA 동작에 영향이 있을 때 생성한다.

- 대상 환경과 현재 상태를 먼저 확인한다.
- 적용 전 검사, 실행 순서, 실패 시 복구, 적용 후 검증을 정의한다.
- dry run과 실제 적용을 구분한다.
- 실제 운영 변경은 사용자 요청 범위 안에서만 수행한다.

## 실행 절차

### 1. 작업을 판별한다

- 목표, 비범위, 제약, 완료 기준을 먼저 적는다.
- 중요한 해석 차이가 결과를 바꾸면 구현 전에 사용자에게 확인한다.
- 안전한 가정으로 진행할 수 있으면 가정과 이유를 밝히고 계속한다.
- 작은 작업이면 이 스킬의 다중 역할 절차를 적용하지 않는다.
- 큰 작업이면 역할별 선택 여부, 투입 단계, 선택하거나 생략한 이유를 역할 선택표로 남긴다.

### 2. 조사 단계를 실행한다

- 현황 조사관에게 읽기 전용 범위와 조사 질문을 전달한다.
- UI와 시스템 설계가 모두 필요하면 제품·경험 설계자와 시스템 설계자를 같은 읽기 전용 단계에서 병렬 실행한다.
- 가용 슬롯이 부족하면 조사, 제품·경험 설계, 시스템 설계를 순차 단계로 실행한다.
- 역할을 합쳐도 독립적인 관점이 사라지지 않는 작은 범위에서만 역할을 겸임시키고 이유를 기록한다.
- 각 결과에서 관찰된 사실, 제안, 미확인 사항을 분리한다.

### 3. 실행 계약을 만든다

전문가 결과를 통합해 다음 내용을 짧게 확정한다.

- 목표와 비범위
- 저장소에서 확인한 근거
- 제품과 기술 결정
- 별도 승인이 필요한 전제조건과 기반 변경
- 구현 단위와 담당 역할
- 역할별 수정 가능 파일과 수정 금지 범위
- 완료 기준과 검증 방법
- 남은 위험과 사용자 결정이 필요한 항목

제품 방향, 데이터 의미, 보안 정책처럼 결과를 크게 바꾸는 결정만 사용자에게 확인한다.

### 4. 구현 단계를 실행한다

- 프론트엔드와 백엔드 파일 소유권이 분리되면 구현자를 병렬 실행한다.
- 공유 타입, 설정, 공통 계약처럼 겹치는 파일은 작업 지휘자가 소유하거나 구현 순서를 정한다.
- 각 구현자에게 목표, 허용 경로, 금지 경로, 결정사항, 완료 기준, 검증 명령을 명시한다.
- 구현자가 범위 밖 문제를 발견하면 임의로 수정하지 말고 작업 지휘자에게 보고하게 한다.

### 5. 통합한다

- 실제 diff와 작업 트리 상태를 확인한다.
- 구현 결과가 실행 계약과 기존 프로젝트 경계를 지키는지 검토한다.
- 중복 구현, 충돌, 임시 코드, 누락된 정리를 해결한다.
- 변경 범위에 맞는 가장 작은 검증부터 실행한다.

### 6. 독립 검증한다

- 독립 검증자에게 사용자의 원래 요청, 실행 계약, 실제 diff, 검증 로그를 제공한다.
- 구현자의 기대 결론이나 자기평가를 정답처럼 전달하지 않는다.
- 차단 문제가 발견되면 원래 구현자 또는 작업 지휘자가 수정하고 관련 검증을 반복한다.
- 수정 후 독립 검증자가 영향을 다시 확인하게 한다.

### 7. 릴리스 경계를 확인한다

- 운영 영향이 있을 때만 릴리스 보호자를 투입한다.
- 로컬 검증, dry run, 실제 적용, 적용 후 확인을 별도 단계로 유지한다.
- 배포가 DB migration을 대신한다고 가정하지 않는다.

### 8. 완료를 보고한다

- 구현 결과와 사용자에게 중요한 결정을 먼저 설명한다.
- 실행한 검증과 결과, 실행하지 못한 검증, 남은 위험을 구분한다.
- 예상하지 않은 작업 트리 변경이 없는지 확인한다.
- 사용자가 요청하지 않은 커밋, push, 배포, production 변경은 수행하지 않는다.

## 서브에이전트 인계 형식

각 역할 요청에는 다음 내용을 포함한다.

- 역할과 단일 목표
- 필요한 저장소 및 사용자 맥락
- 읽기 전용 또는 수정 가능 여부
- 허용 경로와 금지 경로
- 반환할 산출물
- 완료 조건과 검증
- 판단이 필요한 경우 멈추고 보고할 기준

각 역할은 결론, 근거, 대상 파일, 위험, 검증 결과 순서로 간결하게 보고하게 한다.
